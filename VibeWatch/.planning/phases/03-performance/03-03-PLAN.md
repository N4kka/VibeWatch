TVShowDetailViewModel — same pattern as MovieDetailViewModel, with loadTVShowDetails().

Target pattern (remove PRO gate on the READ, keep it on any WRITE/save):
```swift
// Cache read: available to ALL users
if let cached = await DetailCacheService.shared.loadMovieDetail(id: movieId) {
    self.movieDetail = cached
    // Background refresh (non-blocking):
    Task(priority: .utility) {
        let fresh = await networkService.fetchMovieDetails(id: movieId)
        if let fresh = fresh {
            self.movieDetail = fresh
            if isProUser {
                // Cache write: PRO only (unchanged)
                await DetailCacheService.shared.saveMovieDetail(fresh)
            }
        }
    }
    return
}
// No cache entry — fall through to network (same as before for first-ever load)
```

Research context — Discovery and Clips are already cache-first:
- Discovery: DiscoveryPersonalizationService.memoryCache → DB cache → network (correct)
- Clips: ClipsRepository → DatabaseClipsService → ContentCacheManager (correct)
These two paths only need test verification, not code changes.

Note on ClipsViewModel.ensureMinimumLoadingTime():
The 2-second minimum load time in ClipsViewModel is intentional UX policy and does NOT conflict
with PERF-04. PERF-04 means "cache read happens before network call", not "UI appears in under 500ms"
for Clips. Do not remove or modify ensureMinimumLoadingTime().

PERF-04 scope decision: cache READS are extended to all users. Cache WRITES (saving detail data
to DetailCacheService) remain PRO-only. This is the minimal change that satisfies PERF-04 without
changing the PRO feature boundary.
