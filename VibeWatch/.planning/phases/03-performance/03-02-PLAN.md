<objective>
Add a concurrent reader queue alongside the existing serial writer queue in SQLiteService.

Purpose: WAL mode is already enabled but all reads still serialize through the single dbQueue. Opening a second read-only SQLite connection and routing SELECT queries through a concurrent DispatchQueue removes the read-write serialization bottleneck for Discovery, MovieDetail, TVDetail, and Clips cold starts.
Output: SQLiteService has two queues and two connections. Reads are concurrent and non-blocking against writes.
</objective>

```swift
    attributes: .concurrent,
    qos: .userInitiated
)
```

SQLITE flags for read-only connection:
```swift
let flags = SQLITE_OPEN_READONLY | SQLITE_OPEN_NOMUTEX | SQLITE_OPEN_SHAREDCACHE
sqlite3_open_v2(dbPath, &readerDb, Int32(flags), nil)
```

Note: SQLITE_OPEN_SHAREDCACHE is valid on iOS but its benefit is minor; including it matches the
research recommendation. If it causes issues (rare), remove it — READONLY | NOMUTEX is sufficient.

queryRaw() current routing: uses dbQueue.async with a continuation. After this plan it must use
readerQueue + readerDb. The function signature and return type do not change — only the internal
queue and connection handle change.

Existing callers of execute() (writes): all use dbQueue.sync. After renaming to writerQueue, the
internal call `dbQueue.sync` becomes `writerQueue.sync`. No call sites outside SQLiteService need
changing — execute() is a public method, the queue is private.

Callers of queryRaw() outside SQLiteService: many files call `SQLiteService.shared.queryRaw(...)`.
Their call sites do not change — queryRaw() is async and its signature is unchanged.
